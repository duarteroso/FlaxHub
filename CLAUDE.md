# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

The Qt project is in the `flaxhub/` folder. The repo root holds this file, `README.md`, `LICENSE`, `.gitignore`, `.qmllint.ini` and the `build/` folder. Run the commands below from the repo root. Other paths, such as `src/` and `tests/`, are relative to `flaxhub/` unless they say repo root.

## Build and run

Qt 6 Qt Quick app built with CMake (≥ 3.22, the CMake version Qt 6.10's documentation gives for configuring a project on most platforms). Qt 6.12 is installed at `/home/duarteroso/Qt/6.12.0/gcc_64`; the project requires Qt 6.10+.

```
cmake -S flaxhub -B build/Desktop_Qt_6_12_0_Debug -DQt6_DIR=/home/duarteroso/Qt/6.12.0/gcc_64/lib/cmake/Qt6 -DCMAKE_BUILD_TYPE=Debug
cmake --build build/Desktop_Qt_6_12_0_Debug
./build/Desktop_Qt_6_12_0_Debug/appFlaxHub
```

- `build*/` at the repo root is gitignored and follows Qt Creator's `build/<kit>` layout. `build/Desktop_Qt_6_12_0_Debug` is configured with the default compiler; pass `-DCMAKE_CXX_COMPILER=/home/linuxbrew/.linuxbrew/bin/clang++` to use Homebrew clang++ instead.
- Configure needs OpenGL development files (`mesa-libGL-devel` and `libglvnd-devel` on Fedora). Without them, configure fails with `Could NOT find OpenGL` → `Qt6Gui` → `Qt6Quick` not found. They are installed on the Fedora machine.
- The app and the tests build with `-Wall -Wextra`, or `/W4` under MSVC. The flags are set once in `CMakeLists.txt` as `FLAXHUB_WARNING_FLAGS`. Do not disable warnings to make a build pass.

## Tests

```
cmake --build build/Desktop_Qt_6_12_0_Debug
ctest --test-dir build/Desktop_Qt_6_12_0_Debug --output-on-failure
```

The QtTest executables are in `tests/` and are registered with CTest. There are six, and `ctest` runs all of them:

- `tst_installrules` covers `InstallRules::isFullPath`, `isSafeToRemove`, `isFreeFolder`, `expandHome`, `collapseHome`, the marker, `mayUninstall`, `needsClone` and `needsClear`.
- `tst_installvalidator` covers `InstallValidator::validate` for each failed check, including git missing from the PATH or failing, and a complete checkout, and `describe`.
- `tst_installlistmodel` covers `InstallListModel` with a settings file in a temporary folder: restoring saved installs across a restart, relocating (refused unless the folder holds the marker and is a checkout), uninstall, and Fix asking before it clears a folder with files.
- `tst_projectlistmodel` covers `ProjectListModel` with a settings file in a temporary folder: restoring added projects and their last-opened times, refusing duplicates, `open` keeping the quotes in the editor arguments, `create` (refusing duplicates, removing the folder of a failed run), and an install state change not refreshing the projects.
- `tst_enginecatalog` covers parsing GitHub's tag pages and the last-page rule.
- `tst_filemanager` covers `FileManager::folderUrl` and `displayPath`.

The tests use temporary folders only. `tst_installrules` points `HOME` at a temporary folder for its run and restores it afterwards. The two model tests give their models a settings file in a temporary folder, so the user's settings are not read or written. Each test compiles the sources it covers from `src/`, so none of them links the app. The two model tests share one object library, `flaxhub_model_objects`, and `tests/CMakeLists.txt` lists its model sources, so a new source file the models need goes there as well as in the top-level `SOURCES`. The tests are part of the normal build; configure with `-DBUILD_TESTING=OFF` to leave them out.

## Lint

```
qmllint -I build/Desktop_Qt_6_12_0_Debug $(find . -name '*.qml' -not -path '*/build*/*')
```

Run it after a build, since the FlaxHub module's `qmldir` is generated there. `.qmllint.ini` in the repo root holds the qmllint settings and disables nothing. The import path has to come from `-I`: `AdditionalQmlImportPaths` in the ini is resolved against each linted file's folder, so one relative path cannot serve both the root QML files and the subfolders. The command finds the QML files on disk, since `git ls-files` lists deleted files until they are committed and misses new ones. The QML files lint with no errors, but two warnings are expected. The first, that `Theme` is not declared as a singleton, comes from linting `flaxhub/Theme.qml`, where there is no `qmldir`; the generated module declares it as a singleton. The second, that `Qt.application.state` is not a member of `QQmlApplication`, comes from `dialogs/AddInstallDialog.qml`. `QQuickApplication`, which QtQuick declares, has that property, so this looks like a gap in qmllint's type information rather than a bug in the code. There is no format configuration.

## Architecture

A Qt Quick hub app (Unity Hub style): a sidebar with Projects, Installs and Settings views. C++ provides the models, the settings and the bootstrap; the UI lives in QML.

- `main.cpp` sets the organization and application names (used by `QSettings`), filters one Wayland text-input warning, creates `QGuiApplication`, loads the English translation catalogue (see the translation ids note below), creates `QQmlApplicationEngine`, then calls `engine.loadFromModule("FlaxHub", "Main")`. It exits with -1 if the root object fails to create.
- `CMakeLists.txt` defines the executable `appFlaxHub` (project `FlaxHub`) and a QML module with `URI FlaxHub`. Every QML file goes in `QML_FILES`. `SOURCES` lists every C++ file the app compiles, the models and the helpers alike; a file missing from the list is not in the app. `qt_add_translations` compiles `translations/flaxhub_en.ts` into the app's resources. The module URI and the `Main` type in `main.cpp` must match. Renaming `Main.qml`, changing the URI, or renaming the target means updating `main.cpp` and `CMakeLists.txt` together.
- `AppSettings` (`src/appsettings.*`) is a C++ QML singleton that owns the Settings preferences: `installDirectory`, `projectsDirectory` and `editorArguments`. Each is saved to `QSettings` under the `General` group with the same key the QML `Settings` type used, so existing settings still load. The default install folder, `FlaxHub/Engines` in the home folder as a full path, is `InstallLayout::defaultInstallDirectory()` in `src/installlayout.h`: `installDirectory` starts at it, and an install uses it when it names no folder. The projects default is the same kind of full path. A saved `~/...` still works through `expandHome`. A folder setting that is not a full path is refused through `errorOccurred`. Views and dialogs take it as `required property AppSettings prefs`.
- `Main.qml` is the window. It owns the models (`InstallListModel` as `installModel`, `ProjectListModel` as `projectModel`), the sidebar with a `StackLayout` of the three views, the dialogs `AddInstallDialog`, `InstallProgressDialog` and `NewProjectDialog`, and three `ConfirmDialog`s: uninstall, clear folder and quit. `Main.qml` also owns the one `NoticeDialog`, which shows every `errorOccurred` signal from the two models, `AppSettings` and `FileManager`. Closing the window asks first, through the quit `ConfirmDialog`, while an install runs, a folder is being removed or a project is being created.
- `Theme.qml` is a singleton of dark color tokens, spacing, radius, font sizes, and control and layout sizes such as `controlHeight`, `dialogWidth` and `labelWidth`. Use its tokens rather than hard-coded colors or sizes. `Main.qml` also maps the tokens onto `palette`, so Basic controls (ComboBox, Menu, TextField) follow the theme.- Files in `components/`, `views/` and `dialogs/` use `import FlaxHub` to reach `Theme` and each other. `components/` holds the shared pieces: `HubDialog` (the dialog shell: the width, the padding, a body column, and a footer of `buttons` with a `defaultButton` and an `initialFocus`), `ConfirmDialog` (the uninstall, clear-folder and quit confirmations, which default to Cancel), `HubButton`, `HubTextField`, `HubCard` (a row card in the lists), `RowMenuButton` (the "⋮" button and its menu), `SettingsRow`, `SectionLabel` and `HubProgressBar`.
- In a `HubDialog`, Enter presses `defaultButton` while the focus is on a field or on the body, and a focused `HubButton` presses itself. Keys can't be attached to a `Dialog`, so the body is a focus scope that takes Enter. The dialog opens with `initialFocus` focused, or with its default button, or with the body when that button is hidden. `ConfirmDialog` defaults to Cancel, so Enter never confirms a delete.
- Delegates use `pragma ComponentBehavior: Bound` and declare their roles as `required property`. The install's `state` role is read as `model.state`, since every `Item` already has a `state` property. The project row keeps `model` for `setData`.
- `InstallListModel` (`src/installlistmodel.*`) is a `QAbstractListModel` (`QML_ELEMENT`) and the only owner of the install state. Its rows are the release tags, listed as Available, and the installs on disk. It hands the work to the classes below and applies their results as they arrive. `InstallTable` (`src/installtable.*`) holds the rows and the changes of state. `InstallStore` (`src/installstore.*`) saves the installs to `QSettings` (group `Installs`: version, path and default flag per entry) and restores them at startup, through the array helpers in `src/settingsarray.h`. `InstallSteps` (`src/installsteps.*`) runs the steps, `InstallFolderJobs` (`src/installfolderjobs.*`) runs the checks and the deletes on worker threads, and `EngineCatalog` fetches the tags. The model itself runs no process and makes no network request. `installStateChanged` fires on each state change, but not for log or progress lines, so a listener that only needs the installed engines can rely on it.
- `EngineRegistry` (`src/engineregistry.h`) is the abstract base of `InstallListModel`. `ProjectListModel` reads the installed engines through it, so it does not depend on how they were installed.
- `EngineCatalog` (`src/enginecatalog.*`) owns the network manager. It fetches the FlaxEngine release tags from GitHub a page at a time, keeps the version tags and sorts them newest first. It emits `versionsFetched` or `fetchFailed`, and the model turns the versions into Available rows. Only one fetch runs at a time. A successful fetch is kept; a failed one is tried again on the next `fetchAvailableVersions` call.
- `InstallRunner` (`src/installrunner.*`) runs one step of an install in a `QProcess`, and `InstallSteps` names the three steps: `git clone --depth 1` of the release tag, then the engine's `GenerateProjectFiles` script in the clone, then `Binaries/Tools/Flax.Build` with `-buildtargets=FlaxEditor`. The runner merges the output, reports git's clone progress, and emits `finished` or `failed`. The model decides what runs next, and a failed generate or build is retried from that step, since its clone is kept. Installs run one at a time: `startInstall` and `fix` refuse while another install is running, and `busy` is true only while a step runs. Only the newest four versions (`InstallTable::recentVersionCount`) can be installed or fixed: the Add dialog lists only those, and `startInstall` and `fix` refuse the rest.
- `InstallValidator` (`src/installvalidator.*`) runs the checks on a folder. `validate` runs git, so `InstallFolderJobs::check` runs it on a `QtConcurrent` worker, and the model applies the result on the GUI thread. An install is `Checking` while its folder is checked: at startup, after its last step, and before a Fix or a Locate. No git call runs on the GUI thread; the GUI thread only does file checks such as `hasReleaseEditor` and `InstallRules::isFreeFolder`.
- Uninstall deletes the folder on a worker thread, with the entry in the `Removing` state until the delete finishes. It deletes only when `InstallRules::mayUninstall` allows it: the path passes `isSafeToRemove`, and the folder has the marker or is a complete checkout. Any other folder is kept. The entry then becomes `Invalid` with the reason, or, if it was already `Invalid`, it leaves the list and a notice says the folder stays on disk.
- Deletes are guarded by `InstallRules::isSafeToRemove`, which refuses a relative path, a filesystem root, the home folder and any folder that holds the home folder, after resolving `..` and symlinks. It does not limit deletes to the install folder, so a saved path elsewhere under home can still be removed: Uninstall does so only when `mayUninstall` allows it, but a confirmed Fix clears a folder with `isSafeToRemove` alone. A Fix on a folder that has files but is not a checkout asks the user first: the model emits `clearConfirmationRequired`, `Main.qml` opens the clear-folder `ConfirmDialog`, and only a confirmed `fix(version, true)` clears the folder. `relocate` accepts only a folder that holds the FlaxHub marker (`InstallRules::hasMarker`). It refuses any other folder, and a marked folder that is not a checkout of that version, through `errorOccurred`.
- `src/installrules.*` holds the rules for install folders that depend only on paths and validator results: `isFullPath`, `isFreeFolder`, `isSafeToRemove`, `mayUninstall`, `needsClone` and `needsClear`, plus the marker the Hub writes after a clone (`writeMarker`, `hasMarker`; the file is `.flaxhub-install`). `isNewerVersion` is in `src/versionutils.h`. The model and its helpers call them, and the tests call them directly.
- `ProjectListModel` (`src/projectlistmodel.*`) saves its projects to `QSettings` (group `Projects`: name, path, engine version, last opened and pinned per entry) and restores them at startup. A saved project whose folder is gone stays listed, and `open()` reports it through `errorOccurred`. It reads the installs through an `EngineRegistry` pointer set by the `installs` property, and re-emits `EngineInstalledRole` only when the set of installed engines changes. `open(path, editorArguments)` starts the project's editor detached with `-project="<file>"`, followed by the Extra launch arguments from Settings, split at white space outside quotes with the quotes kept, since the engine reads them. `addExisting` (behind Add existing) takes a folder holding a `.flaxproj`, names the project after that file, and takes its engine from `MinEngineVersion`, falling back to `preferredVersion`. `create` (behind `NewProjectDialog`) hands the run to `ProjectCreator` (`src/projectcreator.*`), which runs the installed engine's editor as `FlaxEditor -new -exit -headless -std -project="<dir>"`. The project joins the list only if its `.flaxproj` exists afterwards. A failed run removes the folder the editor made, and quitting stops a run in progress the same way. Only one project is created at a time, and `creating` is true meanwhile. `InstallLayout::editorRelativePath()` in `src/installlayout.h` gives the editor's path per platform, under `Binaries/Editor/<platform>/Release`, and `InstallListModel::editorExecutable` returns it for an installed engine.
- Both models take their `QSettings` through a second constructor, so a test can pass a temporary file. The default constructor, which QML uses, takes the application's settings.
- Failures the user should see are reported through `errorOccurred(title, message)`, which both models emit and `Main.qml` shows in `NoticeDialog`. That covers create, add, open, Locate and Fix refusals. A failed install step is different: its reason is written to the install's log and its state becomes `Failed`, and `InstallProgressDialog` shows it there.
- Texts are translation ids, not English: QML uses `qsTrId("main.<component>.<key>")` and C++ uses `qtTrId(...)`. The root is always `main`, then the view, dialog or component that declares the text (for texts in Main.qml, the dialog object's id), then a key named for the text's role. The English text lives only in `translations/flaxhub_en.ts`, which `main.cpp` and the model tests load. After adding a text, run `cmake --build build/Desktop_Qt_6_12_0_Debug --target update_translations` and type its English into the new empty `<translation>`. Keys never change when the English does.
- `src/filemanager.*` is a `QObject` singleton (`FileManager` in QML). `reveal()` opens a folder through `QDesktopServices`, falling back to the nearest existing parent for a missing path and to the containing folder for a file. `revealLabel` is the menu text for the platform: Finder on macOS, File Explorer on Windows, "Show in folder" elsewhere. `folderUrl()` gives the URL a folder picker opens at (expanding `~`, falling back to the nearest existing folder, then the home folder), and `toLocalPath()` turns the picked URL back into a path. `copyPath()` puts a path on the clipboard. `expandHome()` and `collapseHome()` live in `src/pathutils.h`. `displayPath()` is the text the views show for a path, with the home folder as `~`. Stored and passed paths stay full, so `copyPath` copies the full path. The paths in `errorOccurred` messages go through `collapseHome` too, except a `path_not_full` message, which echoes what the user typed.
- `components/FolderField.qml` shows a folder path with a Browse button. The path is read-only and shown through `FileManager.displayPath`, but a click on it copies the full path through `FileManager.copyPath`, and only Browse changes it, passing the picked folder on through `chosen`. Browse opens at the folder shown. The Settings view uses it for the installs and projects folders, and `AddInstallDialog` and `NewProjectDialog` use it for their locations. `AddInstallDialog`, `InstallsView` and `ProjectsView` open a `FolderDialog` themselves and take the picked URL through `FileManager.toLocalPath`. `AddInstallDialog` builds the folder with `InstallListModel::installPathFor`, which trims the destination and drops trailing slashes, and installs there only when `InstallListModel::canInstallTo` says that folder is missing or empty.
- The Projects view's engine picker lists installed engines and writes the choice back through `engineVersion` via `setData`. It shows the project's engine, and a pick sets its binding again.
- `importedcontent/` is for Figma-to-Qt exports (see its README). If it has a CMakeLists.txt, the top-level build adds it with `add_subdirectory`, but nothing links its targets into `appFlaxHub` yet.
